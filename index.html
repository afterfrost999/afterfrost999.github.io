03

기획 의도

자기 인식에 관심이 높은 20 · 30대는 정작 본인의 장점을 객관적으로 파악하는 일을 어려워합니다.

  1. 부정적 편향

    장점보다 단점이 먼저 떠오름

  2. 과소평가

    자연스럽게 잘하는 것은 장점으로 세지 않음

  3. 좁은 정의

    강점을 특정 영역으로만 한정해서 생각

그래서 장점을 찾는 과정 자체를 도와주는 서비스가 필요하다고 판단해 이 프로젝트를 기획했습니다.

ERD · 서비스 구조도

ERD

ERD에서 신경 쓴 부분

데이터 무결성을 애플리케이션에만 의존하지 않고 DB 제약조건으로 보장

FK · UNIQUE · CHECK 제약조건을 통해 중복 관계와 비정상 데이터를 데이터베이스 단계에서 방지하도록 설계했습니다.

  • UNIQUE (member_id, coin_id)
  • CHECK (count >= 0)
  • UNIQUE (card_id, question_id)
  • CHECK (requester_id <> receiver_id)
  • ON DELETE CASCADE

기존 ERD와의 차이

기존

테이블 간 관계를 표현하는 데 집중

개선

관계뿐 아니라 데이터의 유효성까지 보장하도록 설계

관계를 연결하는 ERD에서, 데이터 무결성을 보장하는 ERD로.

  • HTTPSNginx에서 80 → 443 리다이렉트, SSL 종료

  • 스키마 관리PostgreSQL 스키마를 Flyway 마이그레이션으로 버전 관리

Troubleshooting

운영 중 발생한 장애 3건입니다.

macOS에서는 정상 빌드되지만 Linux 서버에서는 빌드 실패

Linux Clean Build
원인
파일명 대소문자 구분 차이 · Dependency Hoisting · Production Type Check로 로컬에서만 빌드가 통과하던 상태
해결
Clean Linux 환경을 기준으로 import 경로와 의존성 선언을 정리한 뒤 재검증
결과
운영과 동일한 Linux 환경에서 빌드가 통과하며 배포 파이프라인 정상화

배포 직후 502 Bad Gateway 발생, 백엔드가 기동 직후 재시작 반복

Production Crash Loop
원인
systemctl → journalctl 추적 결과, 기동 시 실행되는 Seed 로직이 운영 DB에서 외래키 제약(FK Constraint) 위반
해결
데이터가 없을 때만 Seed가 동작하도록 변경
결과
크래시 루프 해소, 재배포 후 서비스 정상 응답 (502는 증상, 원인은 애플리케이션 기동 단계)

curl은 303 정상 응답, 브라우저에서만 카카오 OAuth 요청이 404

Browser-only OAuth 404
원인
PWA의 Service Worker가 /api 요청까지 가로채 SPA fallback으로 처리, 요청이 서버에 도달하지 않음
해결
API 경로를 Service Worker의 fallback 대상에서 제외
결과
브라우저에서도 로그인 리다이렉트 정상 동작, OAuth 흐름 복구
08

회고

  1. 핵심 도메인은 서버에서 보장해야 한다.

    여러 API 호출로 분산된 비즈니스 로직을 하나의 트랜잭션으로 구성하며 데이터 정합성의 중요성을 경험했습니다.

  2. 로컬에서 동작하는 것과 운영 가능한 것은 다르다.

    OS, 의존성, 환경변수, 데이터베이스 초기화 등 환경 차이가 실제 장애로 이어질 수 있다는 것을 경험했습니다.

  3. 장애를 해결할 때는 정상 구간과 비정상 구간의 경계를 찾는다.

    로그와 요청 흐름을 따라가며 문제 범위를 좁히는 방식으로 원인을 분석했습니다.
